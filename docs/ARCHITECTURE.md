# Выбор технологий

## Рекомендация

**Django 5.2 LTS + PostgreSQL + серверные HTML-шаблоны + обычные CSS/JavaScript.** На сервере — Gunicorn за Nginx, отдельные постоянные тома для медиа и PostgreSQL. Начать с одного приложения и одного сервера. Медиа при росте можно вынести в S3-совместимое хранилище.

Django 5.2 — LTS с исправлениями безопасности не менее трёх лет с апреля 2025: https://docs.djangoproject.com/en/5.2/releases/5.2/. Закреплена проверенная установленная версия в requirements.txt.

- Админка уже умеет права сотрудников, формы, валидацию и загрузку фотографий. Для 1091 товара отдельная CMS не нужна.
- Авторизация, защищённые сессии, CSRF и миграции входят в один фреймворк. Заказы и каталог живут в одной транзакционной базе.
- Серверный HTML подходит индексируемому каталогу. У посетителя нет обязательного ожидания JS-загрузки, шрифтов со стороннего CDN и гидрации. Дополнительные JS-библиотеки подключаются по реальной необходимости.
- PostgreSQL — транзакции и блокировки при оплате/заказах. SQLite используется только локально. Поиск на 1 тыс. карточек достаточно выполнять в базе; полнотекстовый индекс можно добавить позже.
- WebP и резервирование места под изображения уменьшают загрузку и сдвиги. Используются локальные шрифты системы, сетки с контрольными точками и ограничение длины карточек.
- Nginx отдаёт статику и фотографии, Gunicorn обрабатывает приложение. Внешние интеграции отделены от витрины.

Альтернативы: Next.js + headless CMS добавят второй контур авторизации, API и развёртывания; оправданы при отдельных мобильных клиентах и сложном интерактивном интерфейсе. WooCommerce даёт готовую торговлю, но требует дисциплины обновления и совместимости плагинов. Для собственного расширяемого магазина с контролируемыми заказами выбран Django.

## Модель данных

`Category → Product → ProductImage`; `User → Order → OrderItem`. Позиции заказа сохраняют название, артикул и цену на момент оформления. Удаление товара с заказами запрещено; скрытие выполняется флагом публикации. Информационные страницы редактируются независимо от кода.

Заказ: «Ожидает подтверждения» → менеджер уточняет доставку → «Ожидает оплаты» → подтверждённое уведомление Робокассы → «Оплачен» → «Отправлен» с трек-номером. Доставку не объявляем бесплатной и не вычисляем без тарифа. Объёмные детали отправляются посылкой согласно исходным условиям.

## Робокасса

Документация: https://docs.robokassa.ru/ru/pay-interface и https://docs.robokassa.ru/ru/notifications-and-redirects.

Ключи хранятся на сервере. `PAYMENTS_ENABLED=0` по умолчанию. Поддерживается один алгоритм, совпадающий с кабинетом (`ROBOKASSA_HASH`). Тестовые и боевые ключи задаются отдельно при переключении окружения. Проверяем подпись и точную Decimal-сумму, блокируем заказ транзакцией, повторы подтверждаем без повторного изменения. Запросы с неожиданными Shp_* отвергаются: текущий адаптер их не отправляет.

ResultURL: POST `/payments/robokassa/result/`; SuccessURL `/payments/robokassa/success/`; FailURL `/payments/robokassa/fail/`. SuccessURL никогда не меняет статус оплаты. Чек в адаптере ещё не передаётся: до живого использования нужно выбрать схему фискализации и реализовать/проверить её вместе с владельцем.

## Границы первой версии

Нет количественных остатков/резервов, тарифных API доставки, SMTP-рассылки заказов, фоновых задач, email-подтверждения/восстановления пароля, возвратов и автоматической сверки неоплаченных счетов. Корзина привязана к сессии браузера; синхронизация между устройствами не реализована. Финальный SEO-перенос старых адресов и production-конфигурация описаны в плане запуска.
